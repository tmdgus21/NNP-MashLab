# 입력 · 조율 · 추천 · 투표 알고리즘 (R4~R7)

> 정책 동기화 2026-11-16 (`policy-diff-20261116.md`). 이 문서가 구현 기준이며, 아래와 충돌하는 옛 서술(5분 슬롯, 무제한 연장, 전원 완료 즉시 조율, 최다 인원만 남기기)은 폐기되었다.

방식: **비동기 단일 세션(Single-Session) + 자동 마감**, 날짜는 **처음 정한 범위를 절대 넘지 않는다**.
구현 위치: `server-api/schedule/collection.py`(입력 기간·검증·힌트), `coordination.py`(후보·순위, 순수 함수), `service.py`(상태 전이).

## 0. 큰 흐름
```
모임 생성 (이름 + 복수 날짜 선택. 모임 길이 입력 없음. 선택일 ⊆ 오늘~오늘+1개월 KST. 미선택일은 후보·입력 제외)
  └ 입력 기간 24시간: 각자 24시간 × 30분 격자에서 안 되는 칸만 표시 → 완료 (제출 ≠ 조율 시작)
      └ 마감: 참가자 전원 완료 → 3분 유예 후  /  또는 24시간 도달
          ├ 완료자 ≥ 2 → AI 조율 자동 → 후보(2명 이상·연속 60분 이상·지난 시간 제외)
          │     ├ 1개 → 자동 확정
          │     ├ 2개+ → 투표 (그 조율의 완료자만, 선택, 최대 6시간)
          │     └ 0개 → 재조정 (같은 범위의 남은 미래, 내 답 미리 채움, 힌트) ↻ 최대 4회 → 조율 불가
          └ 완료자 < 2 → 24시간 연장 (최대 1회, 범위 안) → 그래도 < 2 → 조율 불가(실패)
```
상수(`coordination.py`): `SLOT_MINUTES=30`, `MIN_CANDIDATE=60분`, `MIN_PEOPLE=2`, `INPUT_WINDOW=24시간`, `ALL_DONE_GRACE=3분`, `MAX_EXTENSIONS=1`, `EXTENSION=24시간`, `REMIND_BEFORE=1시간`, `VOTING_DURATION=6시간`, `VOTE_LEAD=30분`, `MIN_VOTING=1시간`, `MAX_READJUSTS=4`(처음 제외), `MAX_HINTS=5`, `MAX_RANGE=1개월(달력 기준)`, `PURGE_AFTER_DAYS=30`, `MAX_MEMBERS=설정값(부하 테스트로 결정)`
시간 기준: **Asia/Seoul, 서버 시각**. 하루 24시간(00:00–24:00). 모든 구간은 반열린 `[start, end)`, 30분 경계.

## 1. 모임 선택 날짜 (Q35, 2026-11-20)
- 생성: `selectedDates` (또는 하위호환 연속 `startDate`~`endDate`). 조율·시간 제출은 **선택일만** 사용. 레거시 범위 모임은 연속일을 선택일로 확장.
- `starts_at`/`ends_at`은 선택일(또는 범위)의 min~max 호환 봉투.

## 1b. 모임 날짜 범위 (레거시 호환)
- 시작일 ≥ 오늘, 종료일 ≤ **오늘 + 1개월(실제 달력)** — 예: 11/7 → 12/7까지, 1/31 → 2/28(말일 보정)
- "오늘"은 **서버의 한국 시각** 기준. 앱은 서버 시각(응답의 `serverTime`)으로 달력을 그려 기기 시계 오차를 피한다
- 생성 입력은 이름·닉네임·날짜 범위뿐. **모임 길이(duration) 입력 없음** — 후보는 겹치는 가능 구간에서 나온다
- **종료일이 데드라인**: 어떤 단계(하루 연장·재조정)도 `rooms.ends_at`을 바꾸지 않는다. 범위 밖 날짜는 입력·후보·투표 어디에도 없다
- 범위 안에 미래 시간이 1시간 미만만 남으면 그 시점에 바로 **조율 불가**

## 2. 입력 기간 (collection)
- 열리는 때: 모임 생성 시(처음), 재조정 시(1~4회). 범위 = 모임 범위 중 **지금 이후**
- `closes_at = opened_at + 24시간`(기본). 단 `rooms.ends_at`을 넘지 않는다
- **새 참여로 `closes_at`은 절대 바뀌지 않는다**(Q20)
- **참여(join)는 입력 기간이 OPEN이거나 3분 유예 중일 때만 허용**. 그 외(입력 마감·조율 중·투표 중·확정·진행 중·지난 모임·조율 불가·삭제)는 409. 초대만 받고 참여하지 않은 사람은 ACTIVE가 아니므로 "전원 완료" 인원에 세지 않는다. **초대 대기 기능 없음**
- 완료 후에도 마감 전까지 다시 고쳐서 제출 가능(덮어쓰기). **제출은 조율을 시작시키지 않는다**
- **3분 유예 타이머 (Q38, 확정)**:
  1. ACTIVE 멤버 **전원 완료**로 전이되는 순간(완료자 ≥ 2)에만 `grace_until = now + 3분` 설정. **전원 완료 즉시 조율하지 않는다**
  2. 유예 중 기존 참가자가 완료 상태를 유지한 채 **재제출** → 구간만 덮어쓰고 **`grace_until`은 그대로** (3분을 다시 늘리지 않음)
  3. 유예 중 **신규 참가**로 전원 완료가 깨지면 `grace_until = NULL` (유예 취소) → `closes_at` 규칙으로 복귀
  4. 이후 다시 전원 완료가 되면 **새로운** `grace_until = now + 3분` 시작
  5. 마감 판정 시각은 `min(grace_until, closes_at)` 중 도래한 쪽. **`closes_at`이 더 빠르면 데드라인(`DEADLINE`) 우선**, 유예 만료면 `ALL_DONE`
  6. 참가자 1명뿐이면 전원 완료로 유예·마감하지 않는다(“팀원을 초대해 주세요”)
  7. 유예·마감·연장은 `rooms` 행 `FOR UPDATE` + `close_collection_if_due(room_id, now)` **멱등**. 제출·조회·60초 sweep이 같은 함수를 호출. 주기 작업 지연(최대 ~1분)을 막기 위해 조회·제출 시에도 검사
- 마감 시 미완료자는 이번 조율에서 제외, 결과는 열람 가능. **수동 "조율 시작" 버튼·API 없음**
- **마감 시 완료자 판정** (Q24·Q29):
  - 완료자 ≥ 2 → 조율(4절)
  - 완료자 < 2 이고 `extended_count = 0` → 연장 알림 후 `closes_at = min(closes_at + 24시간, rooms.ends_at)`, `extended_count = 1`. `closes_at`이 이미 `rooms.ends_at` 이상이라 늘릴 시간이 없으면 연장 없이 바로 조율 불가
  - 완료자 < 2 이고 `extended_count = 1` → **조율 불가**(`cancelled`). 열어 둔 채로 두지 않는다
  - 연장은 입력 기간(collection)마다 **최대 1회**(`extended_count ≤ 1`), 연장 중 전원 완료 시 위 유예 규칙 동일

## 3. 한 사람의 입력 (단일 세션, 30분 격자)
- 화면: 날짜 열 × 00:00–24:00 **30분 칸**(하루 48칸), Etta 스타일, 드래그·스크롤. **처음엔 전부 '가능'**, 안 되는 칸만 '불가'로 표시
- 중간 상태는 기기 임시 저장, **"완료" 때만 제출**. 서버에는 최종 '가능' 구간(30분 경계)만. 지난 시간·범위 밖 칸은 비활성
- 재조정이면 이전 입력 기간들의 내 답을 합쳐 미리 채워 둔다
- **다른 사람 정보 (Q37, 입력 중)**: 칸별 **가능 인원 수**(제출자 기준)만 보인다. 남의 불가 격자·개인 선택·닉네임별 가능 여부는 입력 중 어디에도 노출하지 않는다(API 응답에도 멤버 식별자 없음)
- 멤버 목록의 닉네임·입력 완료 ✓는 계속 표시

## 4. 조율 (R5·R6) — 입력 마감 시 자동 실행
- 대상 N = 이번 입력 기간 완료자 수 (`schedule_runs.participant_count`), 완료자 ≥ 2일 때만 실행
- **날짜별로** 처리(자정에서 구간 분리). 슬롯 = 30분. 각 슬롯의 가능 집합 `S[t]` = 그 슬롯에 가능한 완료자 집합
- **지난 시간 제외**: 서버 `now`를 다음 30분 경계로 올린 시각 이전 슬롯은 후보 계산에서 제외

### 4-1. 후보 정의 (긴 공통 구간을 자르지 않음)
한 후보 = 하루 안의 반열린 구간 `[L,R)` + 가능 인원 집합 `I` 로,
- `I` = `[L,R)`의 **모든** 슬롯에서 참석 가능한 사람의 교집합 (구간 전체에 걸쳐 가능한 사람만 센다)
- `|I| ≥ 2`, `R−L ≥ 60분`
- **같은 `I`에 대해 최대 구간만 남긴다**: 좌·우로 슬롯 1칸을 더해도 교집합이 그대로 `I`이면 더 짧은 `[L,R)`는 후보가 아니다  
  → 동일 참가자 집합의 불필요한 부분 구간을 중복 생성하지 않음
- **집합이 달라지는 순간마다 끊는 방식은 쓰지 않는다.** 예: A·B 10:00–13:00, C 11:00–12:00 이면
  1. `10:00–13:00` / {A,B} / 2명 / 3시간
  2. `11:00–12:00` / {A,B,C} / 3명 / 1시간  
  둘 다 후보. `{A,B}`의 3시간 구간이 C 때문에 잘리면 안 된다. `10:00–11:00`·`12:00–13:00`({A,B})는 최대가 아니므로 **생성하지 않음**

### 4-2. 계산 절차 (폭증·누락 방지)
1. 날짜·슬롯에 `S[t]`를 만든다
2. 모든 30분 경계 `L < R`(과거 제외)에 대해 교집합 `I(L,R)=⋂ S[t]`를 구한다. `|I|<2`가 되면 그 `L`에서 `R`을 더 늘리지 않아도 된다(교집합은 구간이 커질수록 줄어들거나 같다)
3. `|I|≥2` 이고 `R−L≥60` 이며, `I(L−30,R)≠I` 또는 L이 날의 시작(또는 과거 커트 직후)이고, `I(L,R+30)≠I` 또는 R이 날의 끝일 때만 `[L,R)`+`I`를 후보로 채택 (최대성)
4. `(L,R,I)` 중복 제거. **`max(|I|)`만 남기고 버리지 않음**
5. **정렬 `sort_order`(1=최고)**: `|I|` DESC → `(R−L)` DESC → `L` ASC
6. 혼자만 가능한 구간은 후보 금지. 후보 0개면 5절

표시: ① 가능 요일 ② 날짜별 구간 + **각 후보의 가능한 사람 닉네임**(후보 발표 후). `M=max(|I|)`는 표시용  
**결정은 서버 코드**. Qwen은 설명만 (6절)

## 5. 후보 0개 → 재조정 (Q21·Q31·Q35) — 날짜 확장 없음
1. 재조정 횟수 < 4(처음 제외) → **재조정 입력 기간**을 연다
   - 범위: 모임 범위 중 **지금 이후 남은 미래**(처음과 같은 범위, 날짜는 늘지 않음)
   - 각자 이전 답을 미리 채움 → 늘리기만 하면 됨
   - **"조금만 늘리면 되는 구간" 힌트(5-1)** 표시
   - 연장 알림: "겹치는 시간이 없어요. 조금만 늘리면 조율할 수 있어요 (재조정 n/4회)"
2. 재조정 4회 후에도 없음, 또는 범위에 미래 시간이 1시간 미만 → **조율 불가**
   - `progress_status='cancelled'`, `lifecycle_status='CANCELLED'`
   - 연장 알림 **최종 1회만**: "조율할 수 있는 시간이 없어요. 방장이 모임을 정리할 수 있어요"
- 단계 요약: 처음 → 실패 → 재조정 1~4 → 조율 불가. **처음 실패한 순간부터 힌트**

### 5-1. 조율 유도 힌트 — `collection.near_misses()`
- 계산: 그 입력 기간의 현재 답(미리 채운 답 포함)으로 30분 슬롯 집계, 지난 시간 제외
- **응답·화면에는 인원 수만**(닉네임 없음 — 입력 중 개인정보 기준)
- 종류:
  - **시간 부족**: 2명 이상 겹치지만 60분 미만 → "11/15 19:00–19:30 2명이 겹쳐요. 30분만 더 되면 후보가 돼요"
  - **인원 부족**: 60분 이상인데 1명만 가능 → "11/22 14:00–16:00 1명만 돼요. 한 명만 더 되면 후보가 돼요"
- 개인화: 내가 그 구간을 '가능'으로 두지 않았으면 "**내가** 되면 후보가 돼요", 탭하면 해당 날짜·시간으로 이동
- 정렬: 필요한 변화가 작은 순 → 이른 시각. 최대 5개. 제출마다 다시 계산해 SSE로 갱신
- 첫 입력 기간에는 없음

## 6. AI 요약 (R5) — `schedule/ai_summary.py`
- 후보·M·N·닉네임만 입력(후보 확정 뒤). 한국어 1~2문장(최대 200자). 커밋 후 백그라운드로 `ai_summary` 채움
- `POST http://127.0.0.1:8080/v1/chat/completions`, `QWEN_UNIX_SOCKET` UDS, 모델 `Qwen3-1.7B-Q8_0`, timeout 60s + 전체 65s, 동시 1개
- 실패·형식 위반 → NULL. **Qwen은 설명만**: 출력으로 후보·순위·인원·확정을 바꾸지 않는다. 이메일 금지

## 7. 분기 (R7) — `service.py`의 한 함수에서만

## 8. 투표 — 그 조율의 완료자만, 선택 참여
### 투표 시작 준비 (Q30)
1. 후보를 시작 시각 순으로 본다
2. `voting_ends_at = min(now + 6시간, 가장 이른 후보 시작 − 30분)`
3. `voting_ends_at − now < 1시간`이면 그 가장 이른 후보를 **제외**하고 2로 돌아간다
4. 남은 후보 수로 다시 분기: 0개 → 재조정 / 1개 → 자동 확정 / 2개+ → VOTING
- 제외 수는 `excluded_soon_count`, 화면에 "곧 시작해서 투표 시간이 부족한 후보 n개는 제외했어요"
- 제외 후 `sort_order`는 남은 후보끼리 1부터 다시(정렬 규칙 동일)

### 투표 자격·검증 (서버)
- **투표 대상자 = 이번 조율의 입력 완료자** (Q33, `voter_count = participant_count`). 미완료자·나중 참여자는 열람만 → 투표 시 **403**
- 선택 후보는 **그 사람이 참석 가능한 후보**(`schedule_candidate_members`에 본인 있음)만. 아니거나 다른 조율·없는 후보 id면 **422**. VOTING이 아니거나 마감 후면 409
- **빈 투표 허용**(`candidateIds=[]`): 투표 **완료**로 기록(`schedule_vote_ballots`)하고 득표에는 영향 없음. "미투표"와 구분한다
- 1인 다중 선택, 마감 전 재투표 덮어쓰기. 투표는 선택
- 득표 **수**는 표시, 투표자 개인별 선택은 노출하지 않는다

### 마감·승자
- **조기 마감**: 대상자 **전원이 투표 완료**(빈 투표 포함) → 즉시(`ALL_VOTED`). 아니면 `voting_ends_at`(최대 6시간) 도달(`TIMEOUT`)
- 승자: **plurality**(최다 득표) → 동점이면 `sort_order` 최소 → 0표(전원 빈 투표·무투표)면 1번. `close_voting_if_due(room_id, now)` 멱등
- **확정 후 불변**: `schedule_results`는 한 번만 기록, 이후 투표·제출·재조정·참여·결과 변경 불가
- 방어 검사: 이미 시작한 후보는 승자에서 제외(정상 흐름에선 없음, 경고 로그)
- 투표 시간이 1시간 이하면 임박 알림 없음

## 9. 푸시 알림 (R9) — `schedule/notifications.py`
| 종류 | 발생 시점 | 받는 사람 |
|---|---|---|
| START | 처음 입력 기간 열림(모임 생성), 입력 기간 중 새 참여(본인 제외) | 입력 대상자 |
| START | 투표 시작 | 투표 대상자(입력 완료자) |
| REMIND | `closes_at − 1시간`, `voting_ends_at − 1시간` (마감 시각이 바뀌면 새 기준으로 다시 1회) | 아직 입력/투표 안 한 사람만 |
| EXTEND | 재조정 시작, 입력 기간 하루 연장(1회) | ACTIVE 멤버 전원 |
| EXTEND | **조율 불가 확정 (모임당 1회만)** — 재조정 소진·미래 시간 부족·연장 후에도 완료자 2명 미만 | ACTIVE 멤버 전원 |
- **한 사건 = 알림 1개**. 재조정은 새 입력 기간이지만 START를 따로 보내지 않고 EXTEND 하나로
- `event_key`에 기준 시각 포함(예: `collection:<id>:remind:<closes_at>`)
- 꺼진 종류는 미발송(SKIPPED 기록). **커밋 이후에만** 발송, 실패는 조율·마감에 영향 없음
- 유예·조기 마감으로 끝난 뒤의 임박 알림은 보내지 않는다

## 10. 개인 부담 원칙
- 꼭 해야 하는 일: **입력 1번**(재조정 시 늘리기만). 투표는 선택
- 어떤 사람의 미응답도 진행을 무기한 막지 않는다(자동 마감, 연장 1회 뒤엔 실패), 날짜는 처음 범위를 넘지 않는다
- 실시간 갱신(SSE)은 화면을 볼 때만, 해야 할 때만 푸시

## 11. 삭제·지난 모임·기존 앱 데이터 (R8, Q13)
- 삭제는 방장만. 소프트 삭제(`progress_status='deleted'`, `deleted_at`). 삭제 요청 **30일 뒤 물리 삭제** 정책(정리 배치는 미구현일 수 있음 — 구현 전까지 행은 남는다)
- **지난 모임**(Q39) = Potato Meet에서 **확정된 종료 시각 이후**. 저장 상태가 아니라 `schedule_results` 후보 종료 시각과 `now` 비교. 참여 불가, 열람만
- **기존 조건부 OK 모임**(Q13) ≠ 지난 모임. `schedule_collections`가 없는 방 등: **조회 가능**, 방장만 삭제, 일정·조건·참가·투표·재조율 불가. 자동 변환·일괄 삭제 금지. 데이터가 없으면 이전 작업 없음
