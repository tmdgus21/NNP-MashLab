description: Potato Meet의 기능 구현·수정·버그 수정 요청을 처리합니다. 요구사항(R1~R9) 매핑, 미정 항목 확인, 승인 요청 카드, 답신 대기, 승인 시 작업 브랜치에서 구현·서버/앱 테스트·문서 갱신·완료 보고, 수정 요청 시 계획 재작성, 취소 시 무변경 종료까지 진행합니다. "기능 만들어줘", "구현해줘", "고쳐줘", "버그", "API 추가" 같은 요청이나 「승인:」「수정:」「취소:」 입력에 사용합니다.
model: sonnet
---
1. 요청을 `docs/potato-meet/PRD.md`의 R1~R9에 매핑한다. 해당 없으면 구현하지 않고 "R 목록에 없는 기능입니다. 추가할까요?"라고 묻고 끝낸다.
2. `docs/potato-meet/open-questions.md`에서 관련 미정 항목을, `architecture.md`에서 관련 API·패키지를 찾는다.
3. 현재 브랜치를 확인한다. `main`이면 작업 브랜치(`feature/<이름>`) 생성을 계획에 넣는다.
4. 승인 요청 카드를 보낸다. 이 단계에서는 파일을 수정하지 않는다.
   ```
   ## 승인 요청: <작업 이름>
   - 관련 요구사항: R?
   - 브랜치: feature/...
   - 변경 파일(예정): 경로 — 무엇을   (apps/android / server-api/schedule / 기타)
   - DB 변경: 없음 / 있음(→ schema-change)
   - 운영·기존 파일 변경: 없음 / 있음(경로, 이유)
   - 새 라이브러리: 없음 / 있음(이름·용도)
   - 테스트: 추가·수정할 테스트
   - 결정 필요: 1. … (A / B)
   진행할까요? 「승인:」「수정:」「취소:」로 답해 주세요.
   ```
5. 답신이 올 때까지 기다린다.
6. 「승인:」이면 계획에 적은 파일만 수정한다. 계획 밖 파일이 필요해지면 멈추고 다시 승인을 요청한다.
7. 「수정:」이면 계획을 고쳐 4번 카드로 다시 요청한다. 결정 질문의 답은 `open-questions.md`에 "결정: …"으로 기록한다.
8. 「취소:」이면 아무것도 바꾸지 않고 한 줄로 보고하고 끝낸다. 애매한 답은 승인으로 보지 않고 걸리는 점 하나만 묻는다.
9. `[HOOK] 차단`이 나오면 즉시 멈추고 메시지를 그대로 보고한다. `[HOOK] 확인 필요`가 거절되면 다른 방법으로 우회하지 않는다. 위반 피드백은 바로 고친다.
10. 검증한다: `cd server-api && DATABASE_URL=sqlite:// ADMIN_ENABLED=0 python -m unittest discover -s tests -v`, `cd apps/android && ./gradlew ktlintCheck testDebugUnitTest assembleDebug`. 3번 실패하면 멈추고 원인을 보고한다.
11. 동작이 바뀌었으면 `docs/potato-meet/`를 갱신한다.
12. 커밋은 작업 브랜치에만. push는 사용자가 요청할 때만, main은 절대 아님.
13. 완료 보고: 작업 이름(R?), 브랜치, 변경 파일, 실행한 검증과 결과, 갱신한 문서, 남은 결정.
